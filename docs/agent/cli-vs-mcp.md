# Agent 面试题

## 1. Agent 通过 CLI 和 MCP 调用工具有什么区别？

**一句话：** MCP 是通过标准协议连接一个常驻的中间层（MCP Server），调用注册在里面的工具；CLI 是给 Agent 一个命令行解释器（比如 Bash），让它把自然语言翻译成具体命令去执行。

### 1.1 两种形态分别是什么

- **MCP**：工具以 MCP Server 的形式存在，工具需要注册到 Server 里。Agent 作为客户端连上之后发现工具，按 JSON Schema 传入结构化参数，通过这层中间层完成调用。工具是「自描述」的：名字、功能说明、参数结构都会自动暴露给 Agent。
- **CLI**：给 Agent 一个解释器（比如 Bash）。让它查看当前目录有哪些文件，它就把这句自然语言翻译成 `ls` 这样的具体命令，由解释器找到操作系统里对应的可执行程序去执行，最后拿到文本结果。

### 1.2 MCP 的优缺点

**优点：**

- **一次开发，到处可用**：只要是支持 MCP 的 Agent 都能直接挂载同一个 Server，不用为每个框架重新教一遍，相当于「工具界的 USB-C」。
- **权限控制更好**：鉴权、限流、参数校验都可以集中收敛在 Server 里做；攻击面也从「整个 shell 什么都能敲」缩小成「只暴露出来的几个方法」。
- **结构化可靠**：参数是结构化 JSON，不用拼命令行字符串，没有转义、注入问题，返回结果也是结构化的。

**缺点：费 Token。**

- 每一轮对话，都要把当前所有可用工具的 Schema（名字、描述、参数定义）发给大模型。
- 账要算清楚：只挂一个天气工具可能就几百 Token；工具多了（上百个），光是工具定义就可能几万 Token——费的是「工具数量」，不是「问题简单不简单」。
- 工程上有缓解手段：① prompt caching，工具定义这段固定内容第二次起命中缓存，成本大幅下降；② 按需加载工具，用什么场景才挂载对应的 Server。

### 1.3 CLI 为什么省 Token，代价是什么

- Bash 工具本身的定义极小（本质就是「收一个命令字符串」），而 Bash 这门语言在训练语料里铺天盖地，模型天然就会写。**它吃的是模型的训练先验**，不需要额外用 Schema 一个个解释能力，所以省 Token。
- 代价是**可靠性依赖模型智力**：它可能拼错命令、选错参数，甚至执行危险命令。所以 CLI 方式一般要依赖外部沙箱做隔离兜底。

### 1.4 能力边界：下单这种事为什么得用 MCP

- CLI 能触及的只有**操作系统层面的能力和机器上已安装的程序**。而电商下单、查询商品这种私有业务 API（接口地址、参数、鉴权方式）模型根本不知道。
- 严格说用 `curl` 也能在命令行调 HTTP 接口，所以不是物理上做不到，而是：模型没有针对这些工具训练过，硬猜命令和参数，准确性没有保障。
- 现实中自定义 CLI 是存在的（`gh`、`kubectl`、`lark-cli`），模型靠规范命名和 `--help` 文档能猜个八九不离十。但可靠性是滑点的：
  - 通用命令（`ls`、`git`）：训练语料极多，几乎不会错；
  - 规范的自定义 CLI：靠推断，偶尔错；
  - 完全私有的复杂业务（下单涉及选品、地址、支付、库存校验）：猜错的概率不可忽视。
- 下单这种动作**错误代价高、不可逆**，错一次就是真实损失。所以结论是：不是技术上不能做成 CLI，而是在「模型没被针对性训练过 + 错误代价高」的场景下，MCP 的结构化约束（JSON 参数 + Schema 校验 + Server 端鉴权和确认）是工程上更稳的选择。

### 1.5 一个 Agent 可以同时有多个 CLI 和多个 MCP Server

可以，两者是**并存**关系，模型自行判断选用哪个。比如一个 Agent 本身自带通用 Shell，又额外装了一个飞书的 lark-cli，同时还挂着若干 MCP Server——这是完全正常的形态。很多 MCP Server 底层其实也还是包了一层 CLI 或 HTTP API。

### 1.6 实例：飞书为什么 lark-cli 和 MCP 并行提供

lark-cli 和 MCP 的底层思想确实接近：都是给 Agent 提供工具能力，模型不需要提前学会飞书的接口。但飞书不是二选一，而是面向不同场景并行提供（开放平台本身也提供了官方 MCP 能力）。

- **落地成本与时间线**：平台一般先有成熟的 OpenAPI 和 CLI，复用它把能力暴露给 Agent 成本最低，不需要实现完整的 MCP 协议栈；而 MCP 协议 2024 年底才开始普及。CLI 是快速把平台能力接入 Agent 生态的方式。
- **Token 消耗方式不同**：MCP 连接后一般通过 `tools/list` 一次性拿到全部工具 Schema 注入上下文；lark-cli 则支持按需 `--help` 延迟加载——用到哪个命令才去读它的说明，不用一开始就把整本「工具说明书」塞给模型。
- **串联方式所在的层不同**：CLI 依托操作系统原生子进程，管道 `|` 是内核级的流式串联，前一个命令的输出直接喂给下一个，**数据流不经过模型**，可以把多个命令组合成复杂工作流（这是 GUI 做不到、MCP 也不优雅的地方——MCP 不是不能串联，但串联要由 Agent 层编排，数据全量经过 Agent）。
- **进程模型不同**：CLI 每条命令是短命的一次性子进程，执行完即释放，天然无状态、故障不残留，适合本地终端和批量自动化；MCP Server 是常驻进程，能保持会话状态，代价是状态和故障集中在一个长进程里。
- **适用客户端不同**：CLI 更适合本地终端类 Agent；MCP 作为跨系统通用协议，更适合 Cursor 这类客户端同时对接多个异构外部工具。

反过来看，CLI 的缺点（输出是自由文本要自己解析、参数靠模型推断、权限粒度粗）在飞书这种复杂业务里同样存在，所以结构化、细粒度授权、对非命令行用户友好的 MCP 依然不可替代——这就是两者并行的原因。

### 1.7 一句话总结

> CLI 吃的是模型的训练先验，省 Token，适合通用、低风险、操作系统层面的操作，可靠性靠模型和沙箱；MCP 用每轮携带 Schema 的 Token 成本，换来自描述、结构化校验、集中鉴权和跨 Agent 复用，适合模型没见过的私有业务能力，尤其是错了代价很高的操作。

## 2. 什么是 Bash？

**一句话：** Bash 是一个命令解释器（shell 的一种）。你输入命令后，它负责解析命令、找到对应的可执行程序加载执行、再把结果拿回来。

### 2.1 不是所有命令都会另起进程

Bash 拿到命令后有一套解析顺序：**别名 → shell 函数 → 内建命令 → 外部程序**。

- **内建命令**（`cd`、`echo`、`pwd`、`export`、`source`）直接在 Bash 自己这个进程里执行，不会另起进程。典型是 `cd`：它改变的是 shell 自己的工作目录，如果另起子进程执行，子进程退出后目录变化就丢了，所以它必须是内建的。
- **外部命令**（`ls`、`grep` 这种独立可执行文件）才会另起进程。
- 用 `type 命令名` 可以查看一个命令到底是内建的还是外部程序。

### 2.2 外部命令的完整动作：fork + exec + wait

不是 Bash 把程序加载进自己内存，而是：

1. Bash 先 **fork** 出一个子进程（Bash 自己继续活着）；
2. 子进程通过 **exec** 用找到的可执行文件替换自己并执行；
3. Bash **wait** 等待子进程结束，拿到它的**退出码**（0 表示成功，非 0 表示失败）。

- 查找程序的过程：按 **PATH 环境变量**里的目录依次找，比如 `grep` 的程序一般在 `/usr/bin/grep`，用 `which grep` 可以查看路径。
- 管道 `ls | grep xxx` 的本质：fork 出两个子进程，把前一个的 stdout 接到后一个的 stdin。

### 2.3 「解释器」还体现在执行前的语法解析

在找程序之前，Bash 还要先做一轮解释工作：变量替换（`$HOME`）、通配符展开（`*.md`）、引号处理、管道 `|`、重定向 `>`、`&&` 等。这些语法能力属于 Bash，不属于 `ls`、`grep` 这些程序——这也是它叫「解释器」而不只是「启动器」的原因。

### 2.4 补充：Bash 只是 shell 的一种

同类的还有 zsh、sh、fish。macOS 现在默认的登录 shell 是 zsh，它和 Bash 是同一类东西，基本用法一致。
