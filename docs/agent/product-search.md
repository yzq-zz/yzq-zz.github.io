# 11. 商品搜索工具：从 Demo 到生产的检索链路

> 基于 globex-agent（电商选购 Agent，3,700 商品 / 7,105 SKU 的样例目录）的真实实现，讲清两件事：Demo 里商品搜索工具内部怎么跑；同样一套算法放到生产（百万级商品）应该怎么落地。

## 11.1 一句话总览

商品检索是一条**候选量逐级收窄的漏斗**：查询理解 → 约束分流 → 多路召回与融合 → 型号去重 → 粗排精排 → 实时校验 → 组装返回。

Demo 和生产的算法完全相同（BM25、向量、RRF、跨编码器精排），本质区别是：**Demo 里应用层内存干的倒排、向量、实时数据三件事，生产分别外置给搜索引擎、向量库和商品/库存中台，应用层只负责编排和融合。**

## 11.2 Demo 实现：一次"买剃须刀"的完整流程

以输入"帮我买个剃须刀"为例。

### 11.2.1 主 Agent 决定调哪个工具

主 Agent 先判断意图：

- "帮我买个剃须刀"是**商品推荐请求**，直接调商品检索工具；
- "剃须刀怎么选、看什么参数、价位区间"才是**选购常识问题**，走品类知识 RAG，不查商品库。

调用检索工具时带上结构化参数：查询词、硬约束（预算、配送地等）、返回数量上限。

### 11.2.2 Demo 内部实际有两条路径

**默认路径（混合开关关闭）：向量召回 → 精排 → 后置过滤。** 过滤发生在召回甚至精排**之后**，不是开头。

**混合路径（开关开启）：先算合格商品 ID 白名单 → 双路召回（向量侧尽量带白名单做前置过滤，词项侧全量扫描后过滤）→ RRF 融合 → 精排 → 型号去重 → 截断。**

> 两个容易记错的顺序：① 默认路径不是"先全量过滤再召回"；② 型号去重在精排**之后**，精排内部只有"相同文本只打分一次"的省 token 优化，不是商品去重。

### 11.2.3 五步流程（以完整混合链路为准）

**第 1 步：硬约束过滤。** 品类归到剃须刀、预算、库存、配送地都是硬条件，不交给模型做语义判断，由代码过滤。

**第 2 步：双路召回 + RRF 融合。**

- 词项路（应用层 BM25）：对标题、品牌、品类、描述、卖点、材质等拼接文本做词频匹配。对型号词、外语品牌名、复合词用二元词项和子词匹配保证精确命中。
- 向量路（Qdrant 稠密向量）：查询向量化后按相似度召回，擅长语义泛化——"剃得干净不伤皮肤"没有"剃须刀"三个字也能召回相关商品。
- 融合：两路各取候选窗口（默认 32），用 RRF（倒数排名融合）按**名次**求和。好处是不需要校准 BM25 分和向量余弦分两套量纲，只看相对排名，工程上最稳。

**第 3 步：精排。** 融合候选连同原始查询发给独立 HTTP reranker（跨编码器模型，查询和文档成对编码），按相关性分数重排。只精排这 32 个候选，不全库精排。同型号跨平台文本完全相同时只打分一次再映射回去，节省 token。

**第 4 步：型号去重。** 同一型号在多个平台的上架记录按型号 ID 合并，避免前五名全是同一把剃须刀的不同报价。

**第 5 步：三级降级兜底。**

- 向量服务挂了 → 纯关键词 2-gram 兜底，能出结果但质量差；
- 向量正常、精排挂了 → 按融合顺序直接返回；
- 全部正常 → 完整链路。
- 明确**禁止用聊天模型冒充精排**，配置只接受独立精排服务或关闭，防止"看起来精排在工作、实际是 LLM 拍脑袋排序"。

### 11.2.4 被过滤候选的反馈

只回传**前 3 条**被过滤候选的摘要（商品 ID、标题、品类、价格 + 一个枚举原因），目的是让模型区分"库里没有这个商品"和"有但不满足你的条件"，否则会把超预算商品误答成"没有"。

七种枚举拒因，按固定优先级短路判断：指定 SKU 无库存、整体无库存、品类不符、命中排除材质、缺少要求材质、不配送目标地、超预算。

Demo 的局限：只取遍历顺序的前 3 条，不是"最可惜的 3 个"，也不按原因计数。

### 11.2.5 真实评测数据与口径（面试要能说清边界）

54 条留出场景（金标纠错后同批重算，修正 4 条错标，无新增模型调用）：

| 策略 | Recall@5 | 二元 NDCG@5 |
|---|---:|---:|
| 纯向量 | 94.79% | 0.8986 |
| 混合召回 | 94.97% | 0.8979 |
| 混合 + 精排 | **98.96%** | **0.9682** |

- 完整链路相对纯向量：Recall@5 +4.17 个百分点，NDCG +0.0696（配对 95% 区间 [+0.0188, +0.1294]，显著）；
- **仅混合召回的增益区间跨 0，不能宣称混合召回单独稳定优于纯向量——增益主要来自精排**；
- 检索模块 P95 913.8ms：本机 CPU 跑 ONNX 精排模型的模块耗时（含向量化 + 精排），不是整轮 Agent 响应时间；
- 精排文本去重优化：开发集 reranker 输入 token 86,191 → 35,049（-59%），模块 P95 1,452ms → 856ms（-41%）。

## 11.3 生产架构：七层漏斗

### 11.3.1 技术栈：Demo 选型 vs 生产选型

- **词项召回**：应用层内存 BM25 全量扫描 → Elasticsearch / OpenSearch 分布式倒排集群；
- **向量召回**：单机 Qdrant 本地文件 → Milvus / Qdrant 集群，或直接用 OpenSearch 的 k-NN；
- **商品数据**：SQLite + JSONL 快照 → MySQL/商品库，经 Kafka 把变更同步进搜索引擎和向量库；
- **库存价格**：目录快照 → Redis 缓存 + 商品/库存中台 RPC；
- **精排**：本机 ONNX → GPU 模型服务集群（Triton / TorchServe 部署跨编码器）；
- **查询理解**：主 Agent 现调大模型 → 独立 NLU 服务（规则/小模型为主，大模型兜底）。

一句话：**没有特殊规模瓶颈时召回层用 OpenSearch 一套引擎同时出 BM25、向量和 filter；规模上来再把向量路拆给 Milvus。**

### 11.3.2 七层流程

**1. 查询理解。** 独立 NLU 服务把自然语言拆成语义查询体、结构化硬约束（品类、预算、配送地）、意图类型，并做同义词归一和改写（"刮胡刀"→"剃须刀"）。规则和小模型为主、大模型兜底，控制延迟和成本。

**2. 约束分流（关键设计）。** 按数据变化频率把约束分两类：

- 静态/准静态约束（品类、品牌、材质、支持配送区域）：直接作为 filter **下推给召回引擎**，在参与相关性打分前排除不合格商品；
- 实时约束（库存、价格）：不在召回阶段查——对全库查实时库存中台扛不住；等候选只剩几十个时再批量查。生产是"索引价格粗筛 + 实时价格复筛"两道，防止用陈旧价格错杀或错放。

**3. 多路召回与融合。** 倒排路和向量路并行，各取几十个候选，RRF 融合。有行为数据后加第三、第四路（个性化召回、热销/类目趋势召回）；融合权重从固定 1:1 升级为按类目学习。

**4. 型号去重。** 同型号跨店铺链接合并为一个代表（价格、店铺评分、履约时效综合选代表），其他报价保留，展示时挂载为"其他 N 个报价"。必须在精排前，否则白烧算力。

**5. 粗排 + 精排。** 融合去重后仍有几百候选：毫秒级粗排（统计特征/小模型）砍到几十个 → 跨编码器精排成对打分。精排服务做批量合并、打分缓存、严格超时和熔断，超时退粗排顺序，绝不用聊天模型兜底。

**6. 实时校验与业务重排。** 只对精排后的几十个候选批量查实时库存、价格、运费（Redis 缓存 + 多级剪枝），剔除刚变无货/涨价的；再做同品牌打散保证多样性、个性化加权、广告位按规则混入。库存校验放这一层是刻意的：成本和新鲜度两头占。

**7. 组装返回。** 商品卡 + 按原因聚合计数的过滤反馈，见 11.4.4。

### 11.3.3 横切原则

- **每层独立降级**：单路召回挂了归一化其余权重；精排挂了走粗排；库存服务挂了按索引库存出结果但打"以结算页为准"标；查询理解挂了用原始文本。降级显式打标、分别监控占比，不混进正常效果指标。
- **超时预算倒着分**：从接口总延迟上限倒推，给召回、精排、实时校验分预算，谁超时砍谁。
- **效果门禁两段式**：离线评测集（按类目拆，防整体指标掩盖细分问题）→ 在线 A/B 看点击率、转化率。离线涨点不等于线上收益，Demo 里没证明稳定收益的混合召回，生产必须靠 A/B 证。

## 11.4 面试高频追问

### 11.4.1 静态约束在召回层是怎么用的？BM25 不是只管文本匹配吗？

一次检索请求在引擎内部是两件独立的事：**文本相关性打分 + 结构化字段过滤**。

BM25 只回答"文本和查询词多相关"，不管"配不配送中国"。商品入库时，品类、品牌、配送区域、材质标签建有独立的结构化索引；查询时把"品类=剃须刀 且 配送地包含中国"作为 filter 表达式传入，引擎在 BM25 打分**之前**候选集合就已经被限定。向量库同理，支持带元数据 filter 的 ANN 检索。

所以不是"先 BM25 搜一遍再过滤一遍"，而是**在被 filter 限定过的文档集合内部做相关性检索**。好处：精排配额不浪费给注定不合格的商品；硬约束很严时不会出现"召回 32 个、合格只有 2 个"的凑数问题。

### 11.4.2 召回层用 OpenSearch 还是 OpenSearch + Milvus？

**先用 OpenSearch 一套引擎（主流起步方案）。** BM25、向量 k-NN、filter 一个请求里全部完成，运维一套集群、数据只同步一份、过滤和相关性在同一份索引上天然一致，百万级商品完全够用。Demo 里应用层拼两路结果、手动传白名单的复杂度直接消掉。

**千万/亿级向量规模或对 ANN 性能有更高要求时，才拆成 OpenSearch + Milvus。** 触发点：向量规模超引擎 k-NN 能力、需要更丰富的索引类型（HNSW、量化、磁盘索引）、或公司已有向量中台。代价：数据双写双同步、过滤条件两边保证一致、两套集群和降级逻辑。

判断口径："没有特殊规模瓶颈用 OpenSearch 一套；向量规模超出搜索引擎 k-NN 能力时，倒排留 OpenSearch、向量拆给 Milvus，应用层负责融合。Demo 的应用层 BM25 + Qdrant 就是这套双引擎形态的雏形。"

### 11.4.3 粗排、精排、Embedding 都需要提前训练吗？

分三个层次：

- **不需要训练的**：BM25 是统计算法（只有两个可调参数），倒排索引和 HNSW 向量索引是数据结构构建，都不叫训练；
- **用预训练模型、一般不从头训练的**：Embedding 模型和精排跨编码器（如 BGE 系列）直接部署或调 API，数据积累多了才做领域微调，微调是可选项不是上线前提；
- **必须用自己业务数据训练的**：吃点击/转化行为日志的学习型粗排和个性化模型，只能靠线上数据训；冷启动期先用统计特征粗排（销量、向量分、文本匹配分加权）顶着。

### 11.4.4 被过滤反馈具体怎么做？举个例子

做法：每个被拒候选记录拒因（枚举）、召回阶段的相关性分/排名、标题价格；然后**按原因聚合计数，每个原因只保留分数最高的一个代表**。

例："预算 300 以内、配送到中国的剃须刀"，召回 32 个、合格 8 个、被拒 24 个，反馈为：

- 超预算 18 款，最相关的是"博朗 Series 9 顶配版，349 元"；
- 不支持配送到中国 4 款；
- 当前无货 2 款。

Agent 据此回答："符合条件的有 8 款。另外 18 款超预算，最接近的是博朗 Series 9 顶配版 349 元，预算放宽到 350 可加入比较；4 款不支持直邮中国。"

价值：用户立刻分清**库里没有 vs 条件卡太死**，并直接得到放宽方向，与转化相关，不只是可观测性。

## 11.5 一句话总结

> 相关性算法（BM25、Embedding、RRF、跨编码器精排）在 Demo 和生产是同一套；生产化的核心是**数据按变化频率分层存储、过滤条件尽量下推召回引擎、候选量沿漏斗逐级收窄、重算力只花在小批量候选上、每一级都能独立降级并用离线评测 + 在线 A/B 双重门禁验证收益**。
