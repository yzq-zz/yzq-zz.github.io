# 11. 商品搜索工具：生产级商品检索链路

## 11.1 总：一条候选量逐级收窄的漏斗

生产环境的商品检索分七层：**查询理解 → 约束分流 → 多路召回与融合 → 型号去重 → 粗排精排 → 实时校验与业务重排 → 组装返回**。候选从上千商品一路收窄到最终展示的几个到十几个。

核心思想有三条：

1. **数据按变化频率分层**：静态数据（品类、品牌、配送区域）进搜索引擎和向量库的索引，实时数据（库存、价格）走 Redis + 中台 RPC；
2. **重算力只花在小批量候选上**：跨编码器精排只处理几十个候选，绝不全库精排；
3. **每一层都能独立降级**：任何一路或一个服务挂掉，链路都能出结果，只是质量下降，并显式标记、分别监控。

## 11.2 分：七层流程详解

### 11.2.1 查询理解

在召回之前先有一个独立的查询理解（NLU）服务，把用户的自然语言拆成三样东西：

- **语义查询体**：送去做相关性匹配的部分；
- **结构化硬约束**：品类、品牌、预算、配送地、材质要求；
- **意图类型**：明确型号直达、品类浏览、口语化需求。

它还负责查询改写和同义词归一，比如"刮胡刀"归到"剃须刀"、外语品牌名归一。实现上以规则和小模型为主、大模型兜底——这类调用每次搜索都发生，必须控制延迟和成本，不能把整条 query 的理解都压在大模型上。

### 11.2.2 约束分流：静态约束下推，实时约束后置

约束不能一把梭在应用层过滤，要按数据变化频率分两类：

- **静态/准静态约束**（品类、品牌、材质标签、支持配送区域）：直接作为 filter **下推给召回引擎**，在参与相关性打分之前就排除不合格商品；
- **实时约束**（实时库存、实时报价）：不在召回阶段查——对全库发起实时查询库存价格，中台扛不住。等候选只剩几十个时再批量查。

价格通常做成两道：**索引价格粗筛 + 实时价格复筛**。索引价格允许有延迟，用于在召回层挡掉明显超预算的商品；最终展示前用实时价格复核，防止用陈旧价格错杀或错放。

### 11.2.3 多路召回与融合

**词项路（BM25 + 倒排索引）。** 商品入库时对标题、品牌、品类、描述、卖点、材质等可检索文本建立倒排索引。查询时按词频和逆文档频率算相关性分。它的强项是型号词、品牌名、外语复合词的精确匹配——用户输入"Braun Series 9"，必须精确命中该型号，不能靠语义猜。

**向量路（Embedding + ANN）。** 查询调 Embedding 服务转成稠密向量，在向量索引（HNSW 等）里做近似最近邻搜索。它的强项是语义泛化——用户说"剃得干净不伤皮肤"，文本里没有"剃须刀"三个字，向量也能把相关商品召回。

**RRF 融合。** 两路并行检索，各自取几十个候选，用倒数排名融合：每个候选按它在两路里的名次算分再求和，名次越靠前贡献越大。用名次而不是原始分，是因为 BM25 分和向量余弦分是两套无法直接比较的量纲，RRF 不需要做分数校准，工程上最稳。权重固定 1:1 只是基线，积累线上行为数据后可以按类目学习权重。

有行为数据的公司通常还会加第三、第四路：基于用户行为的个性化召回、热销/类目趋势召回——相关性好不等于用户想买。

### 11.2.4 型号去重

融合之后、精排**之前**，立刻按标准型号去重：同型号跨店铺、跨平台的多个链接合并成一个代表（按价格、店铺评分、履约时效综合选代表），其他报价先保留不丢，最终展示时挂载为"其他 N 个报价"。

这一步的位置很关键：如果不去重，精排的有限名额会被同一把剃须刀的五个链接占满，不同商品反而排不上来，等于白烧精排算力。

### 11.2.5 粗排 + 精排

**粗排。** 融合去重后仍有几百候选，不可能全量送精排。先用毫秒级的轻量粗排砍到几十个：统计特征（销量、评分、文本匹配分、向量分）加权，或一个轻量小模型。

**精排。** 几十个候选连同原始查询发给专用跨编码器（Cross-Encoder）模型：查询和每个商品文本**成对进入模型编码**，输出一个相关性分数，按分数重排。它比"两边各自编码再算余弦"的双编码器精度高，但慢，所以只精排这几十个。

两个工程要点：

- 精排服务要做**批量合并、打分缓存（文档不变时相同查询命中缓存）、严格超时和熔断**；超时就退粗排顺序，绝不拖垮整个搜索接口；
- **禁止用聊天大模型冒充精排**：大模型排序不可复现、贵、输出不稳定，且无法区分"真做了精排"和"模型按常识在猜"，质量门禁会失效。

### 11.2.6 实时校验与业务重排

精排出几十个候选后，**到这一层才批量调实时服务**：实时库存、实时价格、运费、区域限购。剔除刚刚变成无货或涨价的商品。

库存价格校验放这一层是刻意的取舍：召回层有几千候选，实时查中台扛不住；这里只剩几十个，成本和新鲜度两头都占。

校验完再做业务重排：同品牌/同型号打散保证结果多样性、加入个性化权重、商业化广告位按规则混入。

### 11.2.7 组装返回

返回商品卡（价格、库存、配送均来自刚核验过的实时数据，不允许模型编数字），同时附带**被过滤候选的聚合反馈**（做法见 11.3.3），帮助用户区分"库里没有"和"有货但条件不满足"，并给出放宽条件的方向。

## 11.3 关键工程问题

### 11.3.1 召回层技术栈：OpenSearch 一套，还是 OpenSearch + Milvus

**先用 OpenSearch 一套引擎，是主流起步方案。** OpenSearch 同时提供倒排检索和向量 k-NN 检索，并且两者都支持在同一个请求里带结构化 filter：

- 一次查询完成 BM25、向量召回和静态约束过滤；
- 运维一套集群、数据只同步一份；
- 过滤和相关性在同一份索引上执行，结果天然一致。

百万级商品规模完全够用。

**向量规模到千万、亿级，或对 ANN 性能有更高要求时，才拆成 OpenSearch + Milvus 两套引擎。** 触发点通常是：需要更丰富的向量索引类型（HNSW 调参、量化、磁盘索引）、超大规模下带过滤的向量检索性能不足、或公司已有统一向量中台。代价是数据要双写双同步（一般经 Kafka 分发）、过滤条件两边分别保证一致、多维护一套集群和一套降级逻辑。

判断口径：**没有特殊规模瓶颈时一套 OpenSearch；超出引擎 k-NN 能力后，倒排路留在 OpenSearch、向量路拆给 Milvus，应用层负责两路融合。**

其余组件：商品主库用 MySQL 类数据库，变更经 Kafka 同步进搜索引擎和向量库；实时库存价格用 Redis 缓存 + 商品/库存中台 RPC；精排模型用 GPU 模型服务（Triton / TorchServe）部署。

### 11.3.2 静态约束在召回层是怎么生效的

一次检索请求在引擎内部是两件独立的事：**文本相关性打分 + 结构化字段过滤**。

BM25 只回答"商品文本和查询词有多相关"，不管"配不配送中国"。商品入库时，品类、品牌、配送区域、材质标签都建有独立的结构化索引（倒排列表或范围索引）。查询时把"品类=剃须刀 且 配送地包含中国"作为 filter 表达式传入，引擎在 BM25 打分**之前**，候选集合就已经被限定。向量路同理，向量库支持带元数据 filter 的 ANN 检索。

所以不是"先搜一遍再过滤一遍"，而是**在被 filter 限定过的文档集合内部做相关性检索**。这样精排配额不会浪费给注定不合格的商品；硬约束很严时也不会出现"召回 32 个、合格只有 2 个"的凑数问题。

### 11.3.3 被过滤反馈怎么做，举个例子

做法：每个被硬约束挡掉的候选，记录三样东西——拒因（枚举值，如超预算、不配送、无货）、它在召回阶段的相关性分或排名、标题和价格。然后**按原因聚合计数，每个原因只保留分数最高的一个当代表**。

例：用户要"预算 300 以内、配送到中国的剃须刀"，召回 32 个，合格 8 个，24 个被拒，聚合结果为：

- 超预算 18 款，最相关的是"博朗 Series 9 顶配版，349 元"；
- 不支持配送到中国 4 款；
- 当前无货 2 款。

Agent 据此回答："符合条件的有 8 款。另外有 18 款超预算，最接近的是博朗 Series 9 顶配版 349 元，预算放宽到 350 可以加入比较；4 款不支持直邮中国。"

价值有两个：用户立刻分清**库里没有 vs 条件卡太死**；直接给出放宽条件的方向，这对转化有用，不只是可观测性。

### 11.3.4 粗排、精排、Embedding 都需要提前训练吗

分三个层次：

- **不需要训练的**：BM25 是统计算法（只有少量可调参数），倒排索引和 HNSW 向量索引是数据结构构建，都不叫训练；
- **用预训练模型、业务方一般不从头训练的**：Embedding 模型和精排跨编码器都是成熟的预训练模型，直接部署或调 API；积累了足够的领域语料后可以做领域微调，但微调是可选项，不是上线前提；
- **必须用自己业务数据训练的**：吃点击率、转化率等行为日志的学习型粗排和个性化模型，只能靠自己的线上数据训练；冷启动期先用统计特征粗排（销量、评分、向量分加权）顶着。

### 11.3.5 降级链、超时预算与效果门禁

**每层独立降级。** 任一路召回挂了，其余路权重归一化继续出结果；精排挂了退粗排顺序；实时库存服务挂了按索引库存出结果，但商品打"价格库存以结算页为准"的标记；查询理解挂了直接用原始文本检索。每种降级都显式打标，监控按策略分别看占比，不能把降级流量混进正常效果指标。

**超时预算倒着分。** 从整个搜索接口的延迟上限倒推，给召回、精排、实时校验各自分配预算，谁超时砍谁，而不是串行死等。

**效果门禁两段式。** 任何融合权重、精排模型、过滤策略的变更，先过离线评测集（指标要按类目拆开看，整体指标会掩盖细分场景的问题），再上小流量在线 A/B，看点击率、转化率、退款率等真实指标。**离线涨点不等于线上收益。**

## 11.4 总结

> 生产级商品检索 = 静态数据进引擎、实时数据走中台；查询理解和约束分流在召回前完成，BM25 与向量双路并行召回、RRF 按名次融合；型号去重后先粗排再精排，重算力只花在几十个候选上；实时库存价格在最后小批量核验；每层独立降级，所有变更经离线评测和在线 A/B 双重验证。
