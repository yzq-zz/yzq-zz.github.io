# 虚拟线程调度 · 一步步看懂

> 基于 JDK 21 虚拟线程（JEP 444），用「**乘客与座位**」的模型说清 `Continuation.run()` / `yield()` 的调用时机。

[**👉 点击这里打开可交互演示（虚拟线程调度动图）**](/virtual-thread-scheduling.html){target="_blank"}

---

## 一句话总结

虚拟线程 = **乘客**，载体线程 = **座位**。只有坐上座位的乘客才能跑；当乘客要做 I/O 但还没就绪时，他**把座位让出来**（冻结栈帧到堆上 + `yield()`），座位立刻去服务别的乘客——**没有「占着座位等」这回事**。这就是虚拟线程相对平台线程最大的收益：**阻塞的是虚拟线程，不是 OS 线程**。

---

## 角色与基本概念

- **虚拟线程（Virtual Thread, VT）**：极轻量，由 JVM 管理，可创建成千上万；本身**不是 OS 线程**。
- **载体线程（Carrier Thread, C）**：真正的 OS 平台线程，由 `ForkJoinPool` 维护，**并行度 ≈ CPU 核心数**。这是真正能跑代码、能做系统调用的线程。
- **Continuation**：JVM 内部对象，记录一个虚拟线程的执行现场（栈帧 + PC）。
- **StackChunk**：冻结后的栈帧在堆上的存放形式。
- **JEP 444 关键点**：JDK 21 的 `Socket`、`ServerSocket`、`SocketChannel` 等 I/O 类是**虚拟线程感知**的——一旦发现当前线程是虚拟线程且 I/O 不能立即完成，就走「让出」路径，而不是 OS 阻塞。

## 七步流程

### ① 初始状态

```java
Thread.ofVirtual().start(task1);  // → VT-1 就绪
Thread.ofVirtual().start(task2);  // → VT-2 就绪
Thread.ofVirtual().start(task3);  // → VT-3 就绪
```

- VT-1 / VT-2 / VT-3 刚被创建，还没坐上任何载体。它们躺在堆里，是「就绪」状态，排在调度器队列中。
- C1 / C2 / C3 三个载体线程全部空闲。

此时**没有调用任何 `Continuation` 方法**——因为还没有虚拟线程坐上载体。

---

### ② 挂载（Mount）：调度器把 VT-1 分配给 C1

调度器从就绪队列取出 VT-1，选中空闲的 C1。JVM **直接复用 C1 的原生栈**，让 VT-1 的栈搭在 C1 上跑，然后调用：

```java
// 调度器内部大致逻辑
carrierThread.execute(() -> {
    continuation.run();   // ← VT-1 从这里开始跑
});
```

- C1 从「空闲」变成「忙碌」。从这一刻起，C1 的原生栈上跑的就是 VT-1 的代码。
- 对操作系统来说，它只知道 C1 在跑，完全不知道上面还坐了个虚拟线程。

**关键点**：`Continuation.run()` 是虚拟线程「开始执行」的入口；第一次调用就是**从头开始**，执行 `task` 里的代码，直到遇到 yield 或任务结束。

---

### ③ 遇到阻塞：业务代码走到 `socket.read()`

```java
void task() {
    var data = socket.read();  // ← I/O 未就绪，要挂起
    process(data);
}
```

- VT-1 在 C1 上正常跑 Java 代码。跑到 `socket.read()` 时，I/O 还没就绪。
- 如果是平台线程，这里就会把整个 OS 线程挂起。但这是虚拟线程，JDK 21 的 socket 是**虚拟线程感知**的。
- C1 此刻仍在忙碌，正在执行 `socket.read()` 入口处的判断逻辑。

**这一步还没调用 yield()**——先要判断：当前是不是虚拟线程？I/O 能不能立刻完成？如果不能，才走「让出」路径。

---

### ④ 冻结 + Yield：栈帧打包成 StackChunk

JDK 检测到 I/O 不能立即完成 → 决定挂起当前 VT → 触发：

```java
// Continuation.yield() 的效果（内部伪代码，由 JDK I/O 触发）
yield() {
    把当前所有栈帧 → StackChunk 对象（堆上）
    让 run() 返回     // 控制权交回调度器
}
```

- JVM 把 VT-1 整个调用栈的栈帧**打包成 `StackChunk` 对象，冻结到堆上**。局部变量、程序计数器、操作数栈全部原样保存——一个字节都不丢。
- `run()` 返回，C1 上的这个 lambda 执行结束。
- `yield()` 返回 `true` 表示「已挂起」，返回 `false` 表示「任务已完成」。

**关键点**：调用 `yield()` 的是 JDK 内部代码，**不是业务代码自己调**。

---

### ⑤ 卸载（Unmount）：VT-1 下车，C1 被释放

- VT-1 从 C1 上「下车」，回到堆里变成一堆冻结的 `StackChunk`。它的状态是「等待 I/O 完成」，**不占任何载体线程**。
- **C1 立刻恢复空闲**——这是整个模型最关键的一步。C1 **完全没有被阻塞**，可以马上去跑别的虚拟线程。

```
被阻塞的是 VT-1 自己（堆上的一堆对象）
而 C1 一毫秒都没有被阻塞 → 立刻可复用
```

---

### ⑥ 复用载体：同一个 C1 马上拿去跑 VT-2

调度器把刚空出来的 C1 分配给 VT-2。VT-2 进入运行状态。

```
C1: 跑 VT-1 → VT-1 yield 下车 → C1 空闲
C1: 跑 VT-2                          // 无缝衔接，C1 一直在干活
```

**注意**：VT-1 还躺在堆里等 I/O，但 C1 已经在为新任务干活了。这就是「**M 个虚拟线程复用 N 个载体线程**」最直观的样子。

调度器在 C1 上**再次调用 `Continuation.run()`**——不过这次是 VT-2 的 Continuation，从头开始跑。

---

### ⑦ 解冻恢复：I/O 就绪，VT-1 重新挂载

epoll 通知 socket 可读了。调度器把 VT-1 放回就绪队列，这次分配给空闲的 C2。JVM 把堆上的 `StackChunk` **恢复到 C2 的原生栈**，从上次 `yield()` 调用点之后继续执行，就像什么都没发生过。

```java
continuation.run();              // 从 yield() 的返回点继续
var data = socket.read();        // ← 这次立刻拿到数据
process(data);
```

- **又调用了 `Continuation.run()`**，但这次语义不同：不是从头开始，而是「**恢复**」——从上次 yield 的地方往下走。
- 现在 C1 跑 VT-2，C2 跑 VT-1，两个载体线程同时在干活，同时有两个虚拟线程在推进。这就是**并发**。

---

## 关键收获

- **事务级阻塞 vs 线程级阻塞**：平台线程做 I/O 是「线程级阻塞」，整个 OS 线程被挂起；虚拟线程做 I/O 是「虚拟线程级阻塞」，OS 线程立刻释放。这是高并发场景下虚拟线程能撑住成千上万并发的根本原因。
- **载体线程并行度 ≈ CPU 核心数**：所以阻塞虚拟线程实际上不会让「CPU 闲着」，但会让「载体线程**持续有事可干**」。
- **不是所有阻塞都让 yield**：只有 JDK 改造过的 I/O 类（`java.net`、`java.nio.channels` 等）会触发 yield。`synchronized` + `Object.wait()`、JNI 阻塞调用、JUC `Lock.lock()`（JDK 21 部分已支持但需注意）这些都可能**真的阻塞载体线程**——这是虚拟线程调优中最常见的坑。
- **调度器是合作式的**：和 goroutine 类似，虚拟线程只在「真正安全点」让出——也就是 JDK 内部经过改造的阻塞操作。
