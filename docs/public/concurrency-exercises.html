题目 01：双重检查锁定的隐患

来源：《Java并发编程的艺术》P137 知识点：重排序、volatile、DCL 难度：⭐⭐⭐
📝 Bad Case 代码
public class DoubleCheckedLocking {
    private static Instance instance;

    public static Instance getInstance() {
        if (instance == null) {                          // 4: 第一次检查
            synchronized (DoubleCheckedLocking.class) {  // 5: 加锁
                if (instance == null)                    // 6: 第二次检查
                    instance = new Instance();           // 7: 问题的根源
            }
        }
        return instance;
    }
}
❓ 问题
  1. 这段代码已经有"双重检查 + 锁保护"，为什么它仍然是错误的？
  2. 请描述在什么时序下，线程会拿到一个未完全初始化的对象？（提示：第7行不是原子操作）
  3. 请写出至少一种正确的修复方式。
✍️ 你的答案

问题1：为什么是错的

根源在第7行 instance = new Instance() 不是原子操作，可分解为三步：

  1. 分配对象内存空间
  2. 初始化对象（调用构造方法）
  3. 把 instance 引用指向该内存地址

步骤2和3可能被编译器/处理器重排序（3先于2执行）。

问题2：出错时序

线程A执行第7行，发生重排序，先执行了步骤3（引用已赋值）但步骤2（初始化）还没完成；此时线程B执行到第4行第一次检查，看到 instance 不为 null，直接返回——拿到的是还没有初始化完成的对象。

问题3：修复方式

方式一：volatile 禁止重排序（JDK 5+）

public class SafeDoubleCheckedLocking {
    private volatile static Instance instance;  // 关键改动

    public static Instance getInstance() {
        if (instance == null) {
            synchronized (SafeDoubleCheckedLocking.class) {
                if (instance == null)
                    instance = new Instance();
            }
        }
        return instance;
    }
}

方式二：静态内部类（类初始化锁，推荐）

public class InstanceFactory {
    private static class InstanceHolder {
        public static Instance instance = new Instance();
    }
    public static Instance getInstance() {
        return InstanceHolder.instance;  // 首次访问触发类初始化，JVM加锁保证线程安全
    }
}
📚 《Java并发编程的艺术》P136-142，3.8节。volatile方案依赖JSR-133内存模型增强，需JDK 5+。

题目 02：延迟初始化的线程安全问题

来源：《Java并发编程的艺术》P136 知识点：竞态条件、可见性 难度：⭐⭐
📝 Bad Case 代码
public class UnsafeLazyInitialization {
    private static Instance instance;

    public static Instance getInstance() {
        if (instance == null)          // 1: A线程执行
            instance = new Instance(); // 2: B线程也可能同时执行
        return instance;
    }
}
❓ 问题
  1. 什么时序下单例会被破坏（返回两个不同实例）？
  2. 除了返回不同实例，这段代码还有什么更隐蔽的风险？（提示：instance 不是 volatile）
  3. 写出至少两种修复方案，并比较优缺点。
✍️ 你的答案

问题1：单例被破坏的时序

线程A执行到第1行判断 instance == null 为 true，还没执行第2行；线程B此时也执行第1行，同样判断为 true。之后两个线程各自执行第2行，各创建一个对象——返回了两个不同的实例。

问题2：更隐蔽的风险

instance 不是 volatile，存在可见性问题：即使线程A已创建实例，线程B可能仍读到 null（旧值）；也可能读到引用但对象尚未初始化完成（配合重排序）。

问题3：修复方案对比

方案一：同步方法 —— 简单安全，但每次调用都加锁，高频调用性能差。

public synchronized static Instance getInstance() {
    if (instance == null) instance = new Instance();
    return instance;
}

方案二：静态内部类（推荐） —— 利用JVM类初始化锁，线程安全 + 懒加载 + 无同步开销。

public class InstanceFactory {
    private static class InstanceHolder {
        public static Instance instance = new Instance();
    }
    public static Instance getInstance() {
        return InstanceHolder.instance;
    }
}

方案三：volatile + DCL —— 第一次创建后无锁开销，代码较复杂，需JDK 5+。

📚 《Java并发编程的艺术》P136，3.8.1节。

题目 03：volatile能保证计数正确吗

来源：fucking-java-concurrency/WrongCounterDemo 知识点：volatile原子性误区 难度：⭐⭐
💡 可运行复现：在 fucking-java-concurrency 目录执行 ./mvnw compile exec:java -Dexec.mainClass=fucking.concurrency.demo.WrongCounterDemo
📝 Bad Case 代码
public class WrongCounterDemo {
    private static final int INC_COUNT = 100000000;

    private volatile int counter = 0;  // 已经加了volatile

    public static void main(String[] args) throws Exception {
        WrongCounterDemo demo = new WrongCounterDemo();

        Thread thread1 = new Thread(demo.getConcurrencyCheckTask());
        thread1.start();
        Thread thread2 = new Thread(demo.getConcurrencyCheckTask());
        thread2.start();

        thread1.join();
        thread2.join();

        int actualCounter = demo.counter;
        int expectedCount = INC_COUNT * 2;
        if (actualCounter != expectedCount) {
            System.err.printf("Got wrong count! actual %s, expected: %s.%n",
                    actualCounter, expectedCount);
        } else {
            System.out.println("Got right count!");
        }
    }

    private class ConcurrencyCheckTask implements Runnable {
        @Override
        public void run() {
            for (int i = 0; i < INC_COUNT; ++i) {
                ++counter;  // 问题在这里
            }
        }
    }
}
❓ 问题
  1. counter 已经是 volatile 了，为什么最终结果几乎必然小于期望值？
  2. volatile 能保证什么、不能保证什么？
  3. 写出修复方案，并说明它为什么有效。
✍️ 你的答案

问题1：volatile为什么救不了 ++counter

++counter 是"读-改-写"三步的复合操作：读counter → 加1 → 写回。两个线程可能同时读到相同的旧值，各自加1后先后写回——其中一次更新被覆盖丢失。volatile只保证每次读到的都是最新值，但读和写之间的时间窗口它管不了。

问题2：volatile的边界

  • 能保证：可见性（写后其他线程立即可见）、有序性（禁止特定重排序）
  • 不能保证：原子性（复合操作依然会出问题）

问题3：修复方案

方案一：AtomicInteger（推荐，CAS无锁）

private final AtomicInteger counter = new AtomicInteger(0);
// 循环内改为：
counter.incrementAndGet();  // 硬件级CAS保证原子性

方案二：synchronized

private int counter = 0;
public synchronized void increment() { counter++; }

高竞争下 LongAdder 性能更好（分段累加），-counter 场景可用 LongAdder。

📚 参考来源：fucking-java-concurrency/WrongCounterDemo。面试高频误区："加了volatile就线程安全"。

题目 04：信号变量为什么没生效

来源：fucking-java-concurrency/NoPublishDemo 知识点：可见性、JIT优化 难度：⭐⭐
💡 可运行复现：在 fucking-java-concurrency 目录执行 ./mvnw compile exec:java -Dexec.mainClass=fucking.concurrency.demo.NoPublishDemo
📝 Bad Case 代码
public class NoPublishDemo {
    boolean stop = false;  // 普通变量，非volatile

    public static void main(String[] args) throws Exception {
        NoPublishDemo demo = new NoPublishDemo();

        Thread thread = new Thread(demo.getConcurrencyCheckTask());
        thread.start();

        Thread.sleep(1000);
        System.out.println("Set stop to true in main!");
        demo.stop = true;      // 主线程修改信号
        System.out.println("Exit main.");  // main退出了，但子线程还在跑
    }

    private class ConcurrencyCheckTask implements Runnable {
        @Override
        public void run() {
            System.out.println("ConcurrencyCheckTask started!");
            while (!stop) {
                // 主线程已把stop改为true，但这个循环几乎永远退不出去
            }
            System.out.println("ConcurrencyCheckTask stopped!");
        }
    }
}
❓ 问题
  1. 为什么主线程已经写入 stop = true，子线程却可能永远看不到？
  2. JIT编译器可能对这个空循环做什么"坏事"，让问题更必然化？
  3. 写出修复代码，并说明volatile在这里保证了什么。
✍️ 你的答案

问题1：为什么看不到

stop 是普通变量，JMM允许线程把它缓存在工作内存（寄存器/CPU缓存）中。子线程每次循环读的可能一直是自己缓存里的旧值 false，主线程写入主内存的新值对它不可见。

问题2：JIT的"补刀"

JIT发现循环体是空的、stop 在循环中没人改，可能做循环条件外提（hoisting）：把 while (!stop) 优化成 if (!stop) while(true){}——只读一次，之后永远在空转。这就是为什么实践中这个bug"必然复现"。

问题3：修复

volatile boolean stop = false;

volatile保证：每次读都从主内存刷新、每次写立即刷回主内存、禁止相关的指令重排序——子线程必然能看到主线程的写入。

📚 参考来源：fucking-java-concurrency/NoPublishDemo。volatile最典型的用途：状态标志位。

题目 05：对称加锁引发的死锁

来源：fucking-java-concurrency/SymmetricLockDeadlockDemo 知识点：死锁、锁顺序 难度：⭐⭐⭐
💡 可运行复现：在 fucking-java-concurrency 目录执行 ./mvnw compile exec:java -Dexec.mainClass=fucking.concurrency.demo.SymmetricLockDeadlockDemo
程序卡住后可用 jstack <pid> 查看死锁报告
📝 Bad Case 代码
public class SymmetricLockDeadlockDemo {
    static final Object lock1 = new Object();
    static final Object lock2 = new Object();

    public static void main(String[] args) throws Exception {
        new Thread(new Task1()).start();
        new Thread(new Task2()).start();
    }

    private static class Task1 implements Runnable {
        @Override
        public void run() {
            while (true) {
                synchronized (lock1) {      // 先拿lock1
                    synchronized (lock2) {  // 再拿lock2
                        System.out.println("Hello1");
                    }
                }
            }
        }
    }

    private static class Task2 implements Runnable {
        @Override
        public void run() {
            while (true) {
                synchronized (lock2) {      // 先拿lock2
                    synchronized (lock1) {  // 再拿lock1
                        System.out.println("Hello2");
                    }
                }
            }
        }
    }
}
❓ 问题
  1. 描述死锁发生的具体时序。
  2. 死锁的四个必要条件是什么？这段代码各满足了哪条？
  3. 写出至少两种避免方案，并说明分别破坏了哪个条件。
✍️ 你的答案

问题1：死锁时序

  1. 线程1拿到 lock1，正准备拿 lock2
  2. 线程2拿到 lock2，正准备拿 lock1
  3. 线程1等线程2释放lock2，线程2等线程1释放lock1 → 互相等待，永久阻塞

问题2：四个必要条件

  • 互斥：锁同一时刻只能被一个线程持有 ✅
  • 占有并等待：拿着lock1的同时去等lock2 ✅
  • 不可剥夺：synchronized只能由持有者主动释放 ✅
  • 循环等待：1等2、2等1，形成环路 ✅

问题3：避免方案

方案一：全局固定加锁顺序（破坏循环等待）—— 所有线程都先拿lock1再拿lock2：

// Task1 和 Task2 统一改为：
synchronized (lock1) {
    synchronized (lock2) { ... }
}

复杂场景可按对象的 identityHashCode 排序决定先后。

方案二：tryLock + 超时回退（破坏占有并等待）—— 用 ReentrantLock.tryLock()，拿不到第二把锁就释放已持有的锁并重试：

while (true) {
    if (lock1.tryLock(1, TimeUnit.SECONDS)) {
        try {
            if (lock2.tryLock(1, TimeUnit.SECONDS)) {
                try { /* 业务 */ } finally { lock2.unlock(); }
            }
        } finally { lock1.unlock(); }
    }
}

题目 06：秒杀库存扣减的竞态条件

类型：B类 业务场景 知识点：check-then-act、原子扣减 难度：⭐⭐⭐
📝 场景描述

秒杀活动，用户下单扣减库存。面试官给了下面这段扣库存代码，问你有没有问题。

📝 Bad Case 代码
public class StockService {

    /**
     * 扣减库存
     * @param itemId 商品ID
     * @param qty    扣减数量
     * @return true=成功 false=库存不足
     */
    public boolean deductStock(Long itemId, int qty) {
        // 1. 查询当前库存
        Integer stock = stockMapper.getStock(itemId);

        // 2. 判断库存是否充足
        if (stock >= qty) {
            // 3. 扣减库存
            stockMapper.updateStock(itemId, stock - qty);
            return true;
        }
        return false;
    }
}

// Mapper:
// @Select("SELECT stock FROM item_stock WHERE item_id = #{itemId}")
// Integer getStock(Long itemId);
//
// @Update("UPDATE item_stock SET stock = #{stock} WHERE item_id = #{itemId}")
// int updateStock(Long itemId, int stock);
❓ 问题
  1. 这段代码在高并发下会发生什么？请描述具体的出错时序。
  2. 这种"先查后扣"的模式有哪几个维度的问题？
  3. 请写出至少两种修复方案，并比较它们在秒杀场景下的优缺点。
✍️ 你的答案

问题1：高并发下会怎样

经典的 check-then-act 竞态条件：

  1. 线程A查询库存=10，判断 10>=1，准备扣减
  2. 线程B也查询库存=10（还没被A扣减），判断 10>=1
  3. 线程A执行 updateStock(itemId, 10-1=9)
  4. 线程B执行 updateStock(itemId, 10-1=9) —— 库存被覆盖写回9，而不是8

结果：卖了2件但库存只减了1，超卖。

问题2：6维度分析

  • 并发安全：check-then-act 不原子，查询和更新之间有时间窗口 ✅ 核心问题
  • 性能：先查后扣 = 2次DB往返，可以合并为1次条件UPDATE
  • 幂等性：如果用户重复提交订单，没有幂等保护会重复扣减
  • 事务一致性：方法没有 @Transactional，扣减和订单创建可能不在同一事务

问题3：修复方案

方案一：条件原子UPDATE（最推荐，简单有效）

public boolean deductStock(Long itemId, int qty) {
    // 一行搞定：数据库内部"加行锁→判断→更新"是原子的
    int rows = stockMapper.decreaseStock(itemId, qty);
    return rows > 0;  // 0行=库存不足
}

// @Update("UPDATE item_stock SET stock = stock - #{qty} " +
//         "WHERE item_id = #{itemId} AND stock >= #{qty}")
// int decreaseStock(Long itemId, int qty);

优点：1次DB往返、原子操作、无竞态；缺点：高并发下行锁竞争激烈（热点行）。

方案二：Redis预扣 + 异步落库（秒杀场景推荐）

// 1. 活动开始前把库存预热到Redis
//    SET stock:itemId 1000

// 2. 收到请求时Redis原子扣减
Long remaining = redisTemplate.opsForValue().decrement("stock:" + itemId, qty);
if (remaining != null && remaining >= 0) {
    // 3. 扣减成功，发MQ异步落库
    mqTemplate.send("stock-deduct", new StockDeductMsg(itemId, qty));
    return true;
} else {
    // 库存不足，回补
    redisTemplate.opsForValue().increment("stock:" + itemId, qty);
    return false;
}

优点：Redis单线程无竞态、QPS高、DB压力小；缺点：引入Redis+MQ复杂度、需处理Redis和DB最终一致性。

📚 面试高频场景。核心思路：用数据库条件UPDATE替代"先查后扣"，秒杀级用Redis预扣。

题目 07：支付回调重复处理

类型：B类 业务场景 知识点：幂等性、事务、分布式锁 难度：⭐⭐⭐
📝 场景描述

第三方支付平台回调通知支付结果，后端处理回调。支付平台会重试回调（3次），需要保证不重复处理。

📝 Bad Case 代码
@Service
public class PayCallbackService {

    @Resource
    private OrderMapper orderMapper;
    @Resource
    private AccountMapper accountMapper;

    /**
     * 处理支付回调
     * @param orderId    订单ID
     * @param amount     支付金额
     * @param callbackId 回调唯一标识（支付平台提供）
     */
    public void handleCallback(String orderId, BigDecimal amount, String callbackId) {
        // 1. 查订单状态
        Order order = orderMapper.findById(orderId);

        // 2. 如果未支付，执行扣款+标记已付
        if ("UNPAID".equals(order.getStatus())) {
            accountMapper.deductBalance(order.getUserId(), amount);
            orderMapper.updateStatus(orderId, "PAID");
        }
    }
}
❓ 问题
  1. 支付平台重试回调时，这段代码会发生什么？请描述具体时序。
  2. 这段代码按6维度框架分析，有多少个问题？
  3. 请写出修复后的完整代码（要求同时解决幂等、事务、并发问题）。
✍️ 你的答案

问题1：重试时会发生什么

支付平台重试3次回调：

  1. 回调1到达，查到 UNPAID，执行扣款100元，标记 PAID
  2. 回调2到达（重试），查到 PAID（如果回调1已提交），跳过 ✅
  3. 但如果回调2在回调1的事务提交前到达：查到还是 UNPAID，再次扣款100元 + 标记 PAID

结果：用户被重复扣款。这就是 check-then-act 在并发下的竞态。

问题2：6维度分析

  • 并发安全：check-then-act 非原子，两个回调同时到达会都读到 UNPAID ✅ 核心问题
  • 事务一致性：deductBalance 和 updateStatus 不在 @Transactional 内，扣款成功但标记失败会导致数据不一致 ✅
  • 幂等性：没有任何幂等设计——没用 callbackId 做去重，没用唯一约束 ✅ 核心问题
  • 异常处理：扣款成功后标记失败，没有补偿机制 ✅
  • 性能：先查订单再操作，2次DB往返（可以接受，非主要问题）

问题3：修复代码

@Service
public class PayCallbackServiceFixed {

    @Resource private OrderMapper orderMapper;
    @Resource private AccountMapper accountMapper;
    @Resource private StringRedisTemplate redisTemplate;

    private static final String LOCK_PREFIX = "pay:lock:";

    public void handleCallback(String orderId, BigDecimal amount, String callbackId) {
        String lockKey = LOCK_PREFIX + orderId;

        // 1. 分布式锁：防止同一订单的回调并发处理（锁粒度=orderId）
        Boolean locked = redisTemplate.opsForValue()
                .setIfAbsent(lockKey, callbackId, 30, TimeUnit.SECONDS);
        if (locked == null || !locked) {
            return;  // 其他线程在处理，直接返回（支付平台会重试）
        }

        try {
            // 2. 幂等表去重：用callbackId做唯一约束
            try {
                callbackMapper.insert(callbackId, orderId);  // 唯一索引，重复插入抛异常
            } catch (DuplicateKeyException e) {
                return;  // 已处理过，幂等返回
            }

            // 3. 状态机CAS更新：UNPAID → PAID（原子操作，避免check-then-act）
            int rows = orderMapper.casUpdateStatus(orderId, "UNPAID", "PAID");
            if (rows == 0) {
                return;  // 状态已改（已被处理过），幂等返回
            }

            // 4. 扣款 + 标记在同一事务内
            doPayInTransaction(orderId, amount);

        } finally {
            // 5. 释放锁：Lua脚本保证只删自己的锁
            releaseLock(lockKey, callbackId);
        }
    }

    @Transactional(rollbackFor = Exception.class)
    public void doPayInTransaction(String orderId, BigDecimal amount) {
        Order order = orderMapper.findById(orderId);
        accountMapper.deductBalance(order.getUserId(), amount);
        // 插入流水记录...
    }
}

// CAS更新：WHERE条件带旧状态，保证原子性
// @Update("UPDATE orders SET status = #{newStatus} " +
//         "WHERE id = #{orderId} AND status = #{oldStatus}")
// int casUpdateStatus(String orderId, String oldStatus, String newStatus);

三层防护：① 分布式锁防并发 ② 幂等表防重试 ③ 状态机CAS防check-then-act。三者缺一不可。

题目 08：MQ消费：重复消费与顺序问题

类型：B类 业务场景 知识点：幂等、顺序消费、异常重试 难度：⭐⭐⭐
📝 场景描述

订单服务通过RocketMQ发送订单状态变更消息，下游消费端根据消息更新订单。面试官给了下面这段消费代码。

📝 Bad Case 代码
@Component
@RocketMQMessageListener(topic = "order-status-change")
public class OrderStatusConsumer implements RocketMQListener<OrderMessage> {

    @Resource
    private OrderMapper orderMapper;

    @Override
    public void onMessage(OrderMessage message) {
        // 直接根据消息内容更新订单状态
        if ("CREATE".equals(message.getType())) {
            orderMapper.insert(message.getOrder());
        } else if ("PAY".equals(message.getType())) {
            orderMapper.updateStatus(message.getOrderId(), "PAID");
        } else if ("CANCEL".equals(message.getType())) {
            orderMapper.updateStatus(message.getOrderId(), "CANCELLED");
        }
    }
}
❓ 问题
  1. MQ保证At-Least-Once语义（至少投递一次），重复消费时会怎样？
  2. 消息不保证严格顺序时，CREATE 和 PAY 乱序到达会发生什么？
  3. 如果 orderMapper.insert 抛异常，默认行为是什么？有什么风险？
  4. 请写出修复后的代码，要求同时解决幂等 + 顺序 + 异常处理。
✍️ 你的答案

问题1：重复消费

MQ不保证Exactly-Once。同一条 PAY 消息可能投递2次。第二次执行 updateStatus(orderId, "PAID") 不会出错，但如果 CREATE 消息重复消费，insert 会插入重复数据（如果没有唯一约束）。

问题2：乱序到达

如果 PAY 消息先于 CREATE 到达：updateStatus 找不到订单（还没 insert），影响行数为0，但代码没有检查——状态更新"丢失"。之后 CREATE 到达，订单被插入但状态是初始值，PAY 的更新已经丢了。

更糟的情况：CANCEL 在 PAY 之前到达，把状态改成 CANCELLED，然后 PAY 到达又改成 PAID——已取消的订单变成已支付。

问题3：异常风险

insert 抛异常 → RocketMQ 默认重试16次 → 每次都失败 → 达到最大重试后进入死信队列（DLQ）。但如果异常是"插入重复"（唯一约束冲突），那重试只会不断失败，实际上业务是成功的（数据已存在）——把幂等失败当成了系统异常。

问题4：修复代码

@Component
@RocketMQMessageListener(
    topic = "order-status-change",
    consumerGroup = "order-status-consumer",
    // 同一orderId的消息路由到同一队列，保证顺序消费
    selectorExpression = "CREATE || PAY || CANCEL"
)
public class OrderStatusConsumerFixed implements RocketMQListener<OrderMessage> {

    @Resource private OrderMapper orderMapper;

    @Override
    @Transactional(rollbackFor = Exception.class)
    public void onMessage(OrderMessage message) {
        String orderId = message.getOrderId();

        // 1. 幂等：用消息唯一ID做去重（防重复消费）
        if (isProcessed(message.getMsgId())) {
            return;  // 已处理，幂等返回
        }

        // 2. 状态机校验：只允许合法的状态流转
        //    UNPAID → PAID（合法），CANCELLED → PAID（非法，拒绝）
        Order order = orderMapper.findById(orderId);
        if (order != null) {
            if (!isValidTransition(order.getStatus(), message.getTargetStatus())) {
                return;  // 非法状态流转，幂等返回（不抛异常，不重试）
            }
        }

        // 3. 按消息类型处理
        switch (message.getType()) {
            case "CREATE":
                // insert ignore 或 唯一约束兜底
                try {
                    orderMapper.insertOnDuplicateIgnore(message.getOrder());
                } catch (DuplicateKeyException e) {
                    return;  // 已存在，幂等返回
                }
                break;
            case "PAY":
                // CAS更新：只有当前状态是UNPAID才更新
                int rows = orderMapper.casUpdateStatus(orderId, "UNPAID", "PAID");
                if (rows == 0) return;  // 状态已变更，跳过
                break;
            case "CANCEL":
                orderMapper.casUpdateStatus(orderId, "UNPAID", "CANCELLED");
                break;
        }

        // 4. 记录消息已处理
        markProcessed(message.getMsgId());
    }

    private boolean isValidTransition(String from, String to) {
        // 状态机：定义合法流转
        return ("UNPAID".equals(from) && "PAID".equals(to))
            || ("UNPAID".equals(from) && "CANCELLED".equals(to));
    }
}

核心思路：① 幂等表/messageId去重 ② 状态机校验防止乱序 ③ CAS更新保证原子性 ④ 幂等失败不抛异常（不触发重试）。

📚 面试高频：MQ消费的三大坑——重复消费、乱序、异常重试。

题目 09：缓存击穿：热点key过期

类型：B类 业务场景 知识点：缓存击穿/穿透/雪崩 难度：⭐⭐
📝 场景描述

电商商品详情页，用户浏览商品时先查Redis缓存，没命中再查数据库。某热销商品缓存过期瞬间，大量请求同时打到数据库。

📝 Bad Case 代码
@Service
public class ProductService {

    @Resource
    private ProductMapper productMapper;
    @Resource
    private StringRedisTemplate redisTemplate;

    private static final String KEY_PREFIX = "product:";

    public Product getProduct(Long productId) {
        String key = KEY_PREFIX + productId;

        // 1. 查缓存
        Product product = (Product) redisTemplate.opsForValue().get(key);

        // 2. 缓存未命中，查数据库
        if (product == null) {
            product = productMapper.findById(productId);          // 1000个线程同时到这里
            if (product != null) {
                redisTemplate.opsForValue().set(key, product, 30, TimeUnit.MINUTES);
            }
        }

        return product;
    }
}
❓ 问题
  1. 热销商品的缓存过期的瞬间，会发生什么？请描述具体现象。
  2. 如果 productMapper.findById 返回 null（商品不存在），这段代码还有什么隐患？（提示：缓存穿透）
  3. 请写出修复代码，同时解决缓存击穿和缓存穿透。
✍️ 你的答案

问题1：缓存击穿

热销商品缓存过期的瞬间，1000个请求同时发现缓存miss，全部涌入数据库执行 findById。数据库瞬间负载飙升，可能被打挂。这就是缓存击穿——单个热点key过期导致大量请求穿透到DB。

问题2：缓存穿透

如果商品不存在，findById 返回 null，代码不会缓存任何值。攻击者可以不断请求不存在的商品ID，每次都打到数据库——缓存穿透。

问题3：修复代码

@Service
public class ProductServiceFixed {

    @Resource private ProductMapper productMapper;
    @Resource private StringRedisTemplate redisTemplate;

    private static final String KEY_PREFIX = "product:";
    private static final String EMPTY_FLAG = "NULL";  // 空值标记
    private static final long LOCK_TIMEOUT = 5;       // 获取锁超时(秒)

    public Product getProduct(Long productId) {
        String key = KEY_PREFIX + productId;

        // 1. 查缓存
        String cached = redisTemplate.opsForValue().get(key);
        if (cached != null) {
            if (EMPTY_FLAG.equals(cached)) return null;  // 防穿透：空值缓存
            return deserialize(cached);
        }

        // 2. 获取分布式锁（防击穿：只让一个线程去查DB）
        String lockKey = "lock:" + key;
        String lockValue = UUID.randomUUID().toString();
        Boolean locked = redisTemplate.opsForValue()
                .setIfAbsent(lockKey, lockValue, LOCK_TIMEOUT, TimeUnit.SECONDS);

        if (locked != null && locked) {
            try {
                // 3. 双重检查：拿到锁后再查一次缓存（可能已被其他线程填充）
                cached = redisTemplate.opsForValue().get(key);
                if (cached != null) {
                    return EMPTY_FLAG.equals(cached) ? null : deserialize(cached);
                }

                // 4. 查数据库
                Product product = productMapper.findById(productId);

                // 5. 缓存结果（含空值缓存，防穿透）
                if (product != null) {
                    // 随机过期时间，防雪崩
                    int ttl = 25 + ThreadLocalRandom.current().nextInt(10);
                    redisTemplate.opsForValue().set(key, serialize(product), ttl, TimeUnit.MINUTES);
                } else {
                    // 空值也缓存，但时间短（防穿透）
                    redisTemplate.opsForValue().set(key, EMPTY_FLAG, 2, TimeUnit.MINUTES);
                }
                return product;
            } finally {
                // 6. Lua脚本释放锁（只删自己的）
                releaseLock(lockKey, lockValue);
            }
        } else {
            // 没拿到锁，短暂等待后重试读缓存
            sleep(50);
            return getProduct(productId);  // 递归重试
        }
    }
}

三个缓存问题的解决方案：

  • 击穿（热点key过期）→ 分布式锁 + 双重检查，只让一个线程查DB
  • 穿透（查询不存在的key）→ 空值也缓存（短TTL），或布隆过滤器
  • 雪崩（大量key同时过期）→ 过期时间加随机值
📚 面试必考：缓存三大问题（击穿/穿透/雪崩）的识别与解决。

题目 10：Redis分布式锁的5个坑

类型：B类 业务场景 知识点：SETNX非原子、误删锁、锁续期 难度：⭐⭐⭐
📝 场景描述

面试官让你手写一个Redis分布式锁。下面是候选人写的代码，面试官说有5个坑，你来找。

📝 Bad Case 代码
@Service
public class RedisLockService {

    @Resource
    private StringRedisTemplate redisTemplate;

    /**
     * 加锁
     * @param key    锁key
     * @param expire 过期时间(秒)
     */
    public boolean tryLock(String key, long expire) {
        String value = String.valueOf(System.currentTimeMillis());

        // 坑1：SETNX + EXPIRE 非原子
        Boolean locked = redisTemplate.opsForValue().setIfAbsent(key, value);
        if (locked != null && locked) {
            redisTemplate.expire(key, expire, TimeUnit.SECONDS);  // 如果这行之前crash？
            return true;
        }
        return false;
    }

    /**
     * 释放锁
     */
    public void unlock(String key) {
        // 坑2：直接DEL，可能删掉别人的锁
        redisTemplate.delete(key);
    }

    /**
     * 带锁执行业务
     */
    public boolean doWithLock(String key, long expire, Runnable business) {
        if (!tryLock(key, expire)) {
            return false;  // 坑3：没拿到锁直接返回，无重试
        }

        try {
            business.run();  // 坑4：业务执行超过expire，锁已过期但还在跑
                                          // 坑5：没有锁续期机制
            return true;
        } finally {
            unlock(key);
        }
    }
}
❓ 问题
  1. 坑1（SETNX+EXPIRE非原子）：在什么情况下会出问题？后果是什么？
  2. 坑2（误删锁）：描述"删掉别人的锁"的具体时序。为什么 value 用时间戳是错的？
  3. 坑4+5（锁过期+无续期）：业务执行时间超过锁的过期时间会怎样？
  4. 请写出修复后的完整代码，覆盖所有5个坑。
✍️ 你的答案

坑1：SETNX + EXPIRE 非原子

线程执行 setIfAbsent 成功（锁已写入），但还没执行 expire 时进程crash。结果：锁没有过期时间，永久锁死，后续所有请求都拿不到锁。

修复：用 setIfAbsent(key, value, expire, TimeUnit) 一条命令同时设置值和过期时间（Redis 2.6.12+支持）。

坑2：误删锁 + value用时间戳

时序：线程A拿到锁(value=A)，业务执行中锁过期 → 线程B拿到锁(value=B) → 线程A执行完毕调用 delete(key) → 删掉了线程B的锁 → 线程C又拿到锁，A和B同时执行。

value用时间戳是错的：时间戳可预测，其他线程可以猜出来。应该用 UUID.randomUUID()。

修复：释放锁时先判断value是不是自己的（用Lua脚本保证"判断+删除"原子）：

private static final String RELEASE_SCRIPT =
    "if redis.call('get', KEYS[1]) == ARGV[1] then " +
    "  return redis.call('del', KEYS[1]) " +
    "else return 0 end";

public void unlock(String key, String value) {
    redisTemplate.execute(
        new DefaultRedisScript<>(RELEASE_SCRIPT, Long.class),
        Collections.singletonList(key), value);
}

坑4+5：锁过期 + 无续期

线程A拿到锁(expire=10s)，但业务执行了15s。在第10s时锁已过期，线程B拿到锁开始执行。此时A和B都在执行——锁失效，并发安全被破坏。

修复：看门狗(Watchdog)自动续期。启动一个后台线程，每隔 expire/3 时间检查锁是否还属于自己，如果是则延长过期时间。

修复后完整代码

@Service
public class RedisLockServiceFixed {

    @Resource private StringRedisTemplate redisTemplate;
    @Resource private ScheduledExecutorService scheduler;

    private static final String RELEASE_SCRIPT =
        "if redis.call('get', KEYS[1]) == ARGV[1] then " +
        "  return redis.call('del', KEYS[1]) else return 0 end";

    private static final String RENEW_SCRIPT =
        "if redis.call('get', KEYS[1]) == ARGV[1] then " +
        "  return redis.call('pexpire', KEYS[1], ARGV[2]) else return 0 end";

    public boolean tryLock(String key, String value, long expireSeconds) {
        // 坑1修复：SET + EXPIRE 原子化
        Boolean locked = redisTemplate.opsForValue()
                .setIfAbsent(key, value, expireSeconds, TimeUnit.SECONDS);
        return locked != null && locked;
    }

    public boolean doWithLock(String key, long expire, Supplier<Boolean> business) {
        String value = UUID.randomUUID().toString();

        // 坑3修复：自旋重试
        int retry = 0;
        while (!tryLock(key, value, expire)) {
            if (++retry > 3) return false;
            sleep(100);
        }

        // 坑5修复：看门狗续期
        ScheduledFuture<?> watchdog = startWatchdog(key, value, expire, scheduler);

        try {
            return business.get();
        } finally {
            watchdog.cancel(false);
            // 坑2修复：Lua脚本原子释放
            redisTemplate.execute(
                new DefaultRedisScript<>(RELEASE_SCRIPT, Long.class),
                Collections.singletonList(key), value);
        }
    }

    private ScheduledFuture<?> startWatchdog(String key, String value, long expire,
                                               ScheduledExecutorService scheduler) {
        long renewInterval = TimeUnit.SECONDS.toMillis(expire) / 3;
        return scheduler.scheduleAtFixedRate(() -> {
            redisTemplate.execute(
                new DefaultRedisScript<>(RENEW_SCRIPT, Long.class),
                Collections.singletonList(key),
                String.valueOf(TimeUnit.SECONDS.toMillis(expire)));
        }, renewInterval, renewInterval, TimeUnit.MILLISECONDS);
    }
}

5个坑总结：① SETNX+EXPIRE非原子 → 用setIfAbsent合并 ② 误删锁 → UUID+Lua释放 ③ 无重试 → 自旋 ④ 锁过期 → 看门狗续期 ⑤ 无续期机制 → 定时renew

生产推荐直接用 Redisson（RLock），以上所有坑都已内置解决。
